# 프로토콜과 사용 범위

## 접속 인증

서버가 `SERVER_TIME_NONCE`를 보내고, 클라이언트가 ID와 인증 태그를 포함한 `AUTH_REQ`를 반환합니다. 서버가 해당 ID의 공유 키로 검증하고 `AUTH_RES`를 보내면 클라이언트도 서버 태그를 검증합니다.

Boho는 키 소유 증명과 암호 처리를 제공합니다. 키 조회, 최종 접속 승인, 인증 시도 제한, challenge 만료, 연결 종료와 재접속 정책은 상위 애플리케이션이 관리해야 합니다.

## 일반 통신과 E2EE

| 형식 | 보호 범위 | 서버의 역할 |
|---|---|---|
| `ENC_488` | 클라이언트와 서버 사이의 메시지 전체 | 복호화 후 처리·라우팅, 수신 연결에 맞춰 재암호화 |
| `ENC_E2E` | 연결 키로 보호한 라우팅 헤더 + 별도 키로 암호화한 본문 | 헤더만 해석하고 본문은 그대로 중계 |
| `ENC_PACK` | 독립 메시지 또는 저장 데이터 | E2EE에서는 내부 본문 형식으로 사용 |

`ENC_E2E`의 길이 필드는 암호화된 라우팅 헤더 길이를 뜻합니다. 뒤의 본문은 최종 수신자가 E2E 키로 검증·복호화합니다. 키 배포와 상대 신원 확인은 애플리케이션의 책임입니다. 서버가 E2E 본문을 읽지 못하려면 서버에 E2E 키를 제공하지 않아야 합니다.

CongPacket은 TCP 데이터에서 메시지 경계를 구분하는 외부 프레이밍입니다. 자체 암호 인증이나 재전송 검사를 제공하지 않습니다.

## 보안 범위

현재 프로토콜은 SHA-256 기반 자체 암호 구성입니다. 기존 API의 `generateHMAC`/`getHMAC8` 이름과 달리 프로토콜 태그는 표준 HMAC이 아닙니다. `Boho.sha256.hmac` 유틸리티는 표준 HMAC입니다. 이 프로토콜을 표준 AEAD 또는 TLS와 동등한 보안 보장으로 취급하지 마세요.

Boho는 수신 이력·재전송·시간 신선도 정책을 강제하지 않습니다. 유효한 태그만으로 새 메시지임을 알 수는 없습니다. 같은 키에서 전체 salt/nonce 조합의 재사용 방지는 송신 측에서, 재전송 거부는 수신 애플리케이션에서 설계해야 합니다.

사람이 정한 비밀번호를 위한 느린 KDF, 순방향 비밀성, E2E 키 배포는 제공하지 않습니다. 실제 공유 키에는 충분한 엔트로피가 필요합니다.

## 작은 장치의 메시지 크기

최종 수신 tag의 바이트 길이를 `t`, 이진 본문 크기를 `p`라고 하면 일반 암호화 SIGNAL은 `24+t+p`, 링크 암호화를 적용한 E2EE SIGNAL은 `49+t+p`바이트입니다. CongPacket 외부 헤더는 제외한 값입니다.

장치 RX 버퍼가 80바이트라면 각각 `p <= 56-t`, `p <= 31-t`로 제한해야 합니다. 애플리케이션 포장이나 문자열 종료 문자가 있다면 그 크기도 포함해야 합니다. 서버의 quota와 장치의 실제 고정 수신 버퍼가 같은 값이라고 가정하지 마세요.
